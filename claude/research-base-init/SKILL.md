# Adopt a research base

Make a repository's research directory into a research base: layers declared,
the private layer ignored, every committed record carrying frontmatter, and an
index generated by the base's own scripts.

Read [references/research-base-model.md](references/research-base-model.md)
first. Its *Adopting a base in a repository* section is this skill's procedure,
and *Declaring the layers* and *Frontmatter* say what each step writes. Do not
restate them here; follow them. Every key and value a record may carry is in
[references/record.schema.yaml](references/record.schema.yaml).

**The expensive failure is building the new structure beside the old one.** Two
bases in one repository means the old one still holds the real material and the
new one only demonstrates the model. Adoption is a migration, not a rewrite.

## 1. Decide which case this is

Look before writing anything. Exactly one of these holds:

- **A `base.json` already exists.** This is a base already, not an adoption.
  Stop. Run `python ${CLAUDE_SKILL_DIR}/scripts/validate_base.py --base <base>`,
  where `${CLAUDE_SKILL_DIR}` is this skill's own directory, which a Codex agent
  resolves itself, and report what it says; a base that drifted from its
  contract is an audit's job, not this one. Both bundled scripts are
  pre-approved in exactly the form this skill gives them, so type each command
  as written.
- **A research directory exists without `base.json`.** Adopt it in place. Keep
  every directory name it already uses. When more than one directory could be
  the research directory, propose one and ask, never guess.
- **No research directory exists.** Create one with the contract's minimum: a
  private input layer and a committed synthesis layer.

## 2. Declare the layers

Map each layer directory to its kind, the regimes that kind admits, and whether
it is tracked, in the shape *Declaring the layers* shows. **Put the mapping to
the user before writing `base.json`.** A directory's kind is a classification no
file states, so it is asked, not inferred. Then write `base.json` at the base's
root.

**Then keep every tracked layer committable.** Git commits no empty directory,
so a tracked layer holding no file git would commit is absent on every clone:
the scripts pass the base here and refuse it there with
`layer-directory-missing`. For each tracked layer, run
`git ls-files --cached --others --exclude-standard <layer>`. If it lists
nothing, write a layer `README.md`: a few lines on what the layer holds and
that its rules are in the contract. In the create case that is every tracked
layer. A layer that lists anything, an existing `README.md` included, is left
alone. The contract counts a layer's `README.md` as orientation, so it is never
read as a record.

## 3. Ignore the private layer, anchored

The rule must ignore the private layer and nothing else of the same name.

1. **Refuse to continue while anything under it is tracked.** Run `git ls-files`
   on the layer's directory. If it lists anything, stop and report it. An
   ignore rule does not untrack a file, and taking one out of history is the
   user's decision, never a step of this skill.
2. **Probe before writing.** Run `git check-ignore` on a path inside the layer.
   If it is already ignored, write nothing: a second rule for one fact is a
   second copy that can drift.
3. **Otherwise** append `/<base path>/<layer>/` to the repository's root
   `.gitignore`. The leading slash keeps it anchored to that one directory.
4. **Prove it is anchored.** `git check-ignore` the same layer name under some
   other directory, and confirm it is *not* ignored.

## 4. Backfill frontmatter on every tracked record

A record is a Markdown file at the top level of a tracked layer, records that
predate the base included. Give each one the frontmatter *Frontmatter* defines,
drafting from [assets/finding.md](assets/finding.md) for a finding. Preserve
every record's prose.

**Read every record first, and write nothing yet.** Three things below are
decisions no file states, so they go to the user together, in one batch, before
any record's frontmatter is written — for the reason step 2 asks for the layer
mapping. Put each item as its own answerable question.

- **`kind` is the layer's declared kind**, never a guess from the content.
- **`regime`, `status` and `confidence` say what the record actually
  supports.** Read the record. A conclusion stated without checkable evidence is
  `directional`, however confidently it is written. Never raise a confidence to
  make a backfilled record look finished.
- **A value the record already declares is kept.** Where your reading
  disagrees with it, put the disagreement in the batch, quoting the passage that
  disagrees, and change it only if the user agrees. An accepted change moves
  `updated`, because a changed label is a change to what the record claims;
  adding a key the record lacked does not. **Retiring a living record to frozen
  is only ever proposed**: that its evidence is *permanently unavailable* is the
  user's judgement, never a reading.
- **Every living record needs an `authority`, and it is proposed, not chosen.**
  Draft one per living record from what the record itself cites, and put each
  proposal in the batch. Every entry takes a form the audit can locate:
  - a document in the repository, by its path, optionally with the section it
    names;
  - code, by path and symbol, never by line number;
  - an external source, by URL.

  **Read each proposed authority against the claim before proposing it.** A
  source the record cites need not say what the record claims. In the batch,
  say, per proposal, whether the authority *states*, *qualifies*, *is silent
  on* or *contradicts* the claim, quoting the passage that decides it. For a
  first-hand measured claim, propose its instrument, by `path:symbol` and the
  inputs it ran on, as the contract's *Citations* section defines; a private
  input goes in `sources`. Never propose an authority you have not read against
  the claim: a label saying it was not read leaves the first audit unable to
  tell a wrong record from a badly chosen authority.

  A bare label names nothing the audit can fetch, so it may stay in `sources`
  and never goes in `authority`. **A record the user names no authority for
  stays unfinished**: give it every other key your reading supports and leave
  `authority` empty, so the validator reports it as `authority-missing` — the
  contract's *cannot be audited* case, which the audit already reports as such.
  Never fill in a placeholder.
- **Material that cannot carry frontmatter** — an eval set in JSON, a fixture a
  run measured — **is never edited.** Describe it with a new manifest record in
  the same layer, drafted from [assets/manifest.md](assets/manifest.md), whose
  `covers` list names the files.
  - **One manifest per pre-registered run.** It covers every file that binds
    that run, one file per entry, and no file is covered twice.
  - **Its `sources` pin each commit that froze a covered file**, as
    `<repo>@<sha>`, found with `git log` on the file and never guessed. A
    covered file no commit holds has nothing to pin: say so in the batch.
  - **Name its file with a kebab-case slug of what was pre-registered**, never
    for a commit or a date.
  - **Where no file states which run a file belongs to**, propose the grouping
    in the batch rather than guessing.
- A layer's `README.md` and `TEMPLATE.md` are orientation, not records, and no
  manifest takes either name.

## 5. Generate the index

`scripts/index.py` writes the index into the base's `README.md`, between the
index markers, and refuses to run without them.

- **No `README.md`**: write one, a few lines on what the base is and that its
  rules are in the contract, then the index markers on lines of their own.
- **A `README.md` without the markers**: add them in a section of their own at
  the end, and change no existing prose.
- **Markers already present**: write nothing.

The markers are the two lines `scripts/index.py` prints when it refuses a
README without them. Then run
`python ${CLAUDE_SKILL_DIR}/scripts/index.py --base <base>` and the same command
with `--check`. Never fill the block by hand.

## 6. Check the base with its own tooling

Run `python ${CLAUDE_SKILL_DIR}/scripts/validate_base.py --base <base>` and read
its output, not only its exit code. Repeat until it reports no findings, or
none but `authority-missing` on the records step 4 left unfinished, which are
reported rather than fixed.
Any other finding means a step above is unfinished: fix the record, never the
check.

Then report what was adopted: the layer mapping, every layer given a
`README.md` by step 2, whether an ignore rule was written or already held, how
many records were backfilled and at what
confidence, every manifest record written, each record's authority, each label
the user changed or kept against your reading, and every record left
unfinished. **Do not commit**; the user decides when this lands.

## Guardrails

- Do not build a second base beside an existing research directory.
- Do not adopt a base that already has a `base.json`; validate it instead.
- Do not write `base.json` before the user confirms the layer mapping.
- Do not leave a tracked layer holding nothing git would commit.
- Do not overwrite a layer's existing `README.md`.
- Do not continue while anything under the private layer is tracked, and do not
  untrack or rewrite history yourself.
- Do not add frontmatter to pre-registered material or a measured fixture; write
  a manifest record with `covers` instead.
- Do not raise a backfilled record's confidence above what its evidence supports.
- Do not write any record's frontmatter before the user has answered the batch.
- Do not write an authority entry the audit cannot locate; a bare label is not
  one.
- Do not propose an authority you have not read against the claim.
- Do not change a value a record already declares unless the user agrees.
- Do not retire a record to frozen; propose it.
- Do not hand-edit between the index markers.
- Do not commit.
